# Boot screen, kiosk session and hidden cursor (Pi)

FoxDash boots like a finished device: the Ember Deck boot animation appears in
the initramfs, holds on its last frame while the dashboard starts, and then
FoxDash fills the screen. No Raspberry Pi logos, console text, desktop, panel,
window borders or mouse cursor appear at any stage, including FoxDash restarts
and the power-loss countdown.

Install it once on the Pi (it needs `sudo`, and takes a few minutes while the
initramfs is rebuilt), then reboot:

```bash
cd ~/foxdash_lite_textual
sudo deploy/raspberry-pi/install_boot_experience.sh
sudo reboot
```

Undo it with `sudo deploy/raspberry-pi/install_boot_experience.sh --uninstall`
and reboot. That brings back the Raspberry Pi desktop session, the `pix` boot
theme and the original kernel command line. Every system file the installer
changes is copied to `/var/backups/foxdash-boot/<time>/` first.

## What each stage shows

| Stage | What is on screen | Provided by |
|---|---|---|
| Firmware | Black (no rainbow splash) | `disable_splash=1` in `config.txt` |
| Kernel | Black (no logos, no text, no console cursor) | `logo.nologo vt.global_cursor_default=0 loglevel=3 ...`, console moved to `tty3` |
| Initramfs to login | Ember Deck animation: starfield, twinkle, crescent then fox mask | Plymouth theme `foxdash` |
| Compositor start to first dashboard frame | The last animation frame, still | `swaybg` in the FoxDash Kiosk session |
| Normal running, countdown, cancel | FoxDash, fullscreen | lxterminal + Textual |
| FoxDash restart | The last animation frame, then FoxDash again | launcher restart loop + `swaybg` |
| Power-off | FoxDash "POWERING OFF", then the boot animation until power is cut | power manager, then Plymouth's shutdown splash |

### Boot screen

The theme is The Ember Deck's `emberdeck` Plymouth theme
(`EmberEngine/boot/plymouth/emberdeck` in that repository) with the same art,
logo proportion (55% of the short side) and fade timing. It is adapted for the
Pi Zero 2 W and the HyperPixel 4.0:

- The HyperPixel scans out 480x800 portrait and reports a normal panel
  orientation. FoxDash is shown landscape because kanshi rotates the
  compositor output (`transform 270`), but Plymouth runs before that and
  draws on the raw panel. The theme therefore ships `-rot` images turned 90
  degrees clockwise and uses them whenever the screen is portrait.
- Images are pre-sized (800x480 backgrounds, 264 px logo), so nothing is
  scaled at boot.
- The twinkle layers update every third frame (about 17 Hz). Each update
  redraws the whole screen in software, and the CPU is better spent booting.
- Boot messages and the password prompt are left out: the boot is quiet and
  unencrypted, and Plymouth would clip rotated text.

To rebuild the images after changing the Ember Deck art (needs Pillow):

```bash
python tools/build_boot_assets.py --ember-deck /path/to/The-Ember-Deck
```

### Kiosk session

LightDM autologs into the **FoxDash Kiosk** session instead of the Raspberry Pi
desktop. It is the same compositor (labwc), started with its own config
directory (`labwc -C ~/.config/foxdash-kiosk`) rather than the merged desktop
config, so `pcmanfm --desktop`, `wf-panel-pi` and their respawners never start.
That also frees about 50 MB of RAM. Its autostart runs, in order: kanshi
(rotation), swaybg (background), the FoxDash launcher.

The labwc window rule matches the terminal by app_id (`lxterminal`), removes
its decorations and makes it fullscreen as it first maps, so FoxDash never
appears in a window. The launcher's `wlrctl` loop remains as a fallback for
the desktop session.

SSH, Wi-Fi, VNC (`wayvnc`) and the power-management sudoers rule are
unaffected. VNC shows the kiosk session.

### Cursor

Two native labwc mechanisms, no extra service:

1. `XCURSOR_THEME=foxdash-blank` in the kiosk `environment`. Every cursor name
   in every installed theme is linked to one transparent image, so whatever
   labwc or a client asks for draws nothing, from the moment labwc starts.
2. The window rule runs labwc's `HideCursor` action when FoxDash maps, which
   also takes the cursor off the hardware cursor plane.

Check it from SSH: with no cursor, `kmsprint` lists no 64x64 cursor plane with
an `fb-id`.

### Launcher behaviour in the kiosk

`run_dashboard_visible.sh` sees `FOXDASH_KIOSK=1` (set in the kiosk
`environment`) and then:

- hides the terminal's text cursor and clears the screen before FoxDash starts;
- writes its own messages only to `~/CarOBD/logs/obd_visible_runner.log`,
  never to the screen;
- restarts FoxDash in the same fullscreen window if it exits (after 1 s, or
  5 s if it ran for under 10 s, so a crash loop cannot starve the ignition
  monitor), and reopens the terminal if that ever closes;
- exits cleanly on SIGTERM/SIGHUP, so session teardown at power-off is not
  delayed.

The FoxDash command line (including the power-management flags) is in one
place, `start_foxdash()`. Outside the kiosk the launcher behaves as before.

Restart FoxDash over SSH:

```bash
pkill -f "foxdash_lite run"          # restarts in place within a few seconds
```

Stop it until the next boot:

```bash
pkill -f run_dashboard_visible.sh; pkill -f "foxdash_lite run"
```

## Measurements

Measured on the development Pi (Zero 2 W, Raspberry Pi OS 13 trixie, kernel
6.18) with `systemd-analyze` and the runner log.

| | Before | After |
|---|---|---|
| Kernel | 4.8 s | 4.8 s |
| Userspace to `graphical.target` | 18.2 s | 17.7 s |
| Boot to FoxDash launcher start | ~17 s | ~15 s |
| RAM used after boot (`free -m`) | 219 MB of 424 MB | 201 MB of 424 MB |
| FoxDash process CPU | ~102% of one core (see note) | ~102% (unchanged) |
| lxterminal CPU | ~27% | ~26% |
| Desktop processes (`pcmanfm --desktop`, `wf-panel-pi`) | running, ~51 MB RSS | not started |
| New processes | | `swaybg` ~7 MB RSS, idle |
| FoxDash restart (`kill` the python process) | | back in ~2 s, same window |

Both boots were plain `systemctl reboot`s on 2026-11-24. The boot screen
conceals startup without lengthening it: the splash adds no measurable time,
and dropping the desktop makes FoxDash start about 2 s sooner.

The FoxDash main thread already used about one core at `--refresh-hz 10`
before this change. A separate render-path fix in `foxdash_lite/app.py`,
deployed after these measurements under the kiosk launcher, took the main
thread from 93.8% to 18.3% of a core (whole python 102% to 27%, system 33% to
21% busy across 4 cores; car off). lxterminal rose from 27% to 49% because
the dashboard now actually reaches 10 frames a second. That fix is tracked on
its own branch.

## Known limitations

- The Plymouth-to-compositor hand-over could in principle show one black
  frame (the compositor clears the screen before swaybg's first frame). None
  was visible on the development Pi.
- In the kiosk the terminal is hidden from the toplevel list
  (`skipTaskbar`), so the launcher's `wlrctl` fullscreen fallback finds no
  window and gives up after 5 s. That's harmless: the labwc window rule does
  the fullscreen.
- Installing rebuilds the initramfs for every installed kernel (nine on the
  development Pi, about 10 minutes). Re-running the installer skips this when
  the theme is unchanged.
- Plymouth also appears at power-off, after FoxDash's "POWERING OFF" screen.
  It does not delay shutdown.
- `fsck` or other boot messages are not shown on screen; check
  `journalctl -b` over SSH.
